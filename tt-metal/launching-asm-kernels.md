# Launching a `.S` file as a tt-metal kernel

Observed on tt-metal `4f9fa9e0`, Blackhole p150a, TT-KMD 2.7.0-rc1.

**Measured** unless a paragraph says otherwise. Worked examples in
`tt-loop-scheduler`:

* `example/standalone/matmul_multi_core/` — the original: five kernels (BRISC,
  NCRISC, three TRISCs), `generate_asm_kernel.sh`, `asm_kernel_shim.hpp`, and the
  checked-in `asm_kernel/*.S`.
* `example/standalone/add_2_integers_in_riscv/` — the small one: a single BRISC
  kernel, same mechanism, no compute half and no circular buffers. Useful as the
  minimal reference when the matmul one is too much to read at once.

## The finding

tt-metal has no "assemble this file" entry point, and it does not need one.
`CreateKernelFromString` already lets you choose the *kernel source*, and the
kernel source is textually `#include`d into a firmware translation unit at a
fixed point. So a kernel source that is nothing but an inline-asm `.include` of
a `.S` file splices that assembly in, and `kernel_main` comes from the `.S`:

```cpp
asm(R"ttasm(
.text
.include "/abs/path/to/kernel.S"
)ttasm");
```

Everything else — the entry point, the linker script, the runtime arguments, the
circular buffers — stays tt-metal's. `SetRuntimeArgs` needs no changes, because
`get_arg_val<>()` reads the same `rta_l1_base` the firmware sets up.

## Where the kernel source is spliced in

This is the part worth knowing, because it determines what the `.S` can and
cannot rely on:

| kernel | entry source tt-metal compiles | how the kernel source gets in |
| --- | --- | --- |
| compute (TRISC0/1/2) | `<runtime>/tt_metal/hw/firmware/src/tt-1xx/trisck.cc` | `trisck.cc` → `chlkc_list.h` → `chlkc_<role>.cpp` → kernel source. `chlkc_<role>.cpp` and `chlkc_descriptors.h` are generated by `tt_metal/jit_build/genfiles.cpp` into the kernel's JIT build directory, which the compile has on `-I.` |
| dataflow (BRISC/NCRISC) | `.../tt-1xx/brisck.cc` / `ncrisck.cc` | the entry source itself does `#include "kernel_includes.hpp"`; that file (written by genfiles into the same build directory, found through `-I.`) is `void kernel_main();` + `#include "<kernel source>"` |

So the `TRISC_UNPACK` / `TRISC_MATH` / `TRISC_PACK` defines are already in effect
when your source text appears, and so is `COMPILE_FOR_TRISC`; `NOC_MODE`,
`NOC_INDEX`, `PROCESSOR_INDEX`, `KERNEL_COMPILE_TIME_ARGS` arrive as `-D` on the
command line. A shim can therefore dispatch on `#if defined(TRISC_UNPACK)` and
pick a different `.S` per RISC.

The `-include` in a real JIT compile command is the **PCH**, not
`kernel_includes.hpp`. That tripped up the first version of the generator: it
passed `-include kernel_includes.hpp` *and* let `ncrisck.cc` include it by name,
which included the kernel source twice and produced a wall of redefinition
errors. Reproduce the JIT recipe exactly — write `kernel_includes.hpp` into a
directory you compile from, and pass no `-include`.

## Four things that break, and why

These are the failure modes that cost the time. Each one is silent-ish: the
first three surface as a link error whose message points somewhere unhelpful.

### 1. `-flto=1` drops globals that only the assembly references

The JIT compiles with `-flto=1 -flto-partition=one`. The optimizer cannot see
symbol references inside an `asm(...)` block, so a firmware global that only the
assembly touches looks unreferenced and LTO removes its definition:

```text
undefined reference to `noc_reads_num_issued'
```

Fix: name each such symbol from C++ and keep a `[[gnu::used]]` pointer to it, so
the reference is visible to the optimizer:

```cpp
extern "C" char keep[] asm("noc_reads_num_issued");
[[gnu::used]] static const void* p = keep;
```

Needed for the dataflow kernels: `noc_reads_num_issued`,
`noc_nonposted_writes_num_issued`, `noc_nonposted_writes_acked` (and their
siblings). Needed for the compute kernels: `ckernel::regfile`,
`ckernel::pc_buf_base` (mangled `_ZN7ckernel7regfileE`,
`_ZN7ckernel11pc_buf_baseE`), `unp_cfg_context`, `pack_sync_tile_dst_ptr`,
`math_sync_tile_dst_index`, `gl_alu_format_spec_reg`, `op_info_offset`.

### 2. LLK headers hold per-TU `static` state, and the assembly needs it

`tt_metal/tt-llk/tt_llk_blackhole/common/inc/cmath_common.h` defines

```cpp
static std::uint32_t src_zero_flag_hw       = 0xff;
static std::uint32_t src_zero_flag_srca_fmt = 0xff;
static std::uint32_t src_zero_flag_srcb_fmt = 0xff;
inline __attribute__((noinline)) void _apply_src_zero_flag_(std::uint32_t);
```

— internal linkage, one copy per translation unit. When the kernel was compiled
from C++ those definitions existed because `kernels/compute/mm.cpp` included
`api/compute/matmul.h`. With the assembly spliced in, no C++ code reads them, so
LTO drops them and the link stops with:

```text
undefined reference to `ckernel::math::src_zero_flag_hw'
```

Fix: the shim source must `#include` the headers the kernel included (copy them
out of the kernel source, don't hardcode), and must *pin* the statics. Because
they have internal linkage you cannot use the `asm("name")` alias trick from §1
— you have to spell them out as C++ and take their address in the same TU:

```cpp
[[gnu::used]] static const void* const keep = &ckernel::math::src_zero_flag_hw;
```

The same applies to any other LLK state a kernel's assembly reaches.

### 3. A function pointer in `.data` is rejected at program load

Pinning `_apply_src_zero_flag_` by taking its address compiles and links, then
fails when the program is loaded:

```text
trisc1.elf: unexpected dynamic relocations
```

That check is `tt_metal/llrt/tt_memory.cpp:84`: `tt_elffile.cpp` turns
`R_RISCV_32` relocations **that point into text** into "dynamic relocations"
(`emit dynamic R_RISCV_32 relocation`), and the loader refuses them. A pointer to
`.bss`/`.data` is fine; a pointer to a function is not.

Fix: keep the function alive by **calling** it from a `[[gnu::used]]` static
function instead of storing its address. The call becomes an ordinary
`R_RISCV_CALL` resolved at link time.

```cpp
[[gnu::used]] static void keep_apply_src_zero_flag(std::uint32_t v) {
    ckernel::math::_apply_src_zero_flag_(v);
}
```

### 4. `.L<n>` labels collide, because lto1 re-assembles the TU

With `-flto=1` the final machine code is emitted and assembled by `lto1` **at
link time**, in one assembly stream that also contains the compiler's own output
for the firmware code. A `.L12` from the included `.S` and a `.L12` the compiler
generated for the surrounding C++ are the same symbol to the assembler:

```text
/tmp/ccXXXX.s:192: Error: symbol `.L12' is already defined
```

Fix: namespace every local label the generated `.S` emits, e.g.
`.L12` → `.Lmm_trisc1_math_12`. A `.S` meant to be spliced into someone else's
translation unit must not use file-scoped label names.

## Generating the `.S` faithfully

The only reliable recipe is: copy a real JIT compile command and change `-c` to
`-S`. Capture one with

```bash
TT_METAL_LOGGER_LEVEL=info TT_METAL_LOGGER_TYPES=BuildKernels \
TT_METAL_LOG_KERNELS_COMPILE_COMMANDS=1 \
TT_METAL_CACHE=<a fresh cache dir> <your program>
```

`TT_METAL_LOG_KERNELS_COMPILE_COMMANDS` is what turns on the
`g++ compile cmd:` log line (`tt_metal/jit_build/build.cpp:811`); without it the
BuildKernels logger prints only cache statistics. A **fresh** cache directory is
required, because the log line is inside the compile path and a cache hit skips
it. Note the optimisation level differs by RISC: `-O2` for DM RISCs, `-O3` for
the compute RISCs.

Then reproduce the generated inputs too — `defines_generated.h`, `chlkc_*.cpp`,
`chlkc_descriptors.h` for compute; `kernel_includes.hpp` for dataflow. A real JIT
cache directory is the reference for what those files contain
(`<cache>/<build_key>/kernels/<name>/<hash>/`).

Use `-fno-lto` for the `-S` compile. With `-flto` the final code is produced by
`lto1` at link time and `-S` would hand you a partially optimised body; without
it, cc1's complete `-O2`/`-O3` rendering is what you get, which is what makes the
`.S` self-contained.

## Editing the `.S` does not invalidate the JIT cache

The cache key is the **kernel source string** — for a shim launch that is the
inline-asm text, which contains the `.S` file's *path* and not its contents. The
C preprocessor does not track `.include` inside an `asm(...)` block either, so
the `.S` never enters the key, and `.dephash` does not save you: that mechanism
covers `#include`d **headers**, not assembled `.include`s.

**Measured** on `add_2_integers_in_riscv` (tt-metal `4f9fa9e0`, Blackhole p150a):
after inserting a `nop` into the checked-in `.S`, a re-run with the same
`TT_METAL_CACHE` reported `7/7 hits` and produced a **byte-identical** kernel ELF
(same md5). The same run with a fresh `TT_METAL_CACHE` reported `0/7 hits` and a
different ELF. So the edit is silently ignored — no warning, no rebuild.

Workaround: point `TT_METAL_CACHE` at a fresh directory (or delete the kernel's
entry) after touching a `.S` that a shim launch consumes. This is not specific to
the example it was measured on; it applies to any `.S` spliced in this way.

## DPRINT is compile-time, and it does not survive the `.S` round trip by default

`DPRINT`/`DEVICE_PRINT` is gated at **compile** time from a **run-time**
environment variable: `tt_metal/jit_build/build.cpp` appends
`-DDEBUG_PRINT_ENABLED` only when the DPRINT run-time feature is enabled, and
what enables it is `TT_METAL_DPRINT_CORES`. A kernel therefore has two different
compilations depending on the environment of the *host run*, and a `.S`
generated from the default (no `TT_METAL_DPRINT_CORES`) command is the plain
program: **a spliced `.S` never prints, even with `TT_METAL_DPRINT_CORES` set**,
because the print code has to be in the assembly at all.

Generating the printing variant takes more than adding the define. **Measured**
on `add_2_integers_in_riscv`'s kernel, `-DDEBUG_PRINT_ENABLED` additionally
needs:

1. The `.device_print_strings` / `.device_print_strings_info` sections carried
   over. The format string, the file string and the `DevicePrintStringInfo`
   record that points at both live **outside** `kernel_main`, and an extractor
   that keeps only `kernel_main` produces an `.S` referencing a label nothing
   defines. `kernel_main` reaches the record through the `.LANCHOR<n>` anchor
   (`.set .LANCHOR0, . + 0`), which then needs namespacing like any other local
   label.
2. Pins on `device_print_detail::begin_message_write` /
   `end_message_write`. They are `__attribute__((noinline))` inline functions
   defined in `api/debug/device_print.h`; with the assembly spliced in, no C++
   code calls them, so `-flto` drops them:

   ```text
   undefined reference to `device_print_detail::begin_message_write(device_print_detail::structures::DevicePrintHeader, unsigned int)'
   undefined reference to `device_print_detail::end_message_write()'
   ```

   §3's trick applies — keep them alive by *calling* them from a
   `[[gnu::used]]` static function — but the pin has to be conditional on
   `DEBUG_PRINT_ENABLED`, which couples the `.S` to the environment of the run
   that loads it. A `.S` that only links when an env var happens to be set is a
   trap; shipping the plain program is the safer default.

A dataflow kernel also reaches `chlkc_descriptors.h` only on this path:
`dprint.h` includes `dprint_tile.h` under `KERNEL_BUILD`, which includes it. The
JIT writes that file into every kernel's build directory regardless of kernel
type, so reproduce it (`-I.`) and a DPRINT-enabled regeneration compiles.

## Instrumented kernels: `-DENABLE_TRACY=0` is not enough

If the kernel carries device profile regions behind a wrapper macro, switching
the macro off is not the same as removing the wrapper. Measured on
`matmul_multi_core`'s compute kernel: `PROFILED_IF(enabled, name, ...)` is not
`#if`-guarded, so with `ENABLE_TRACY=0` it still expands to

```cpp
do { if (enabled) { ((void)0); X; } else { X; } } while (0)
```

with `enabled = profile_kt_iteration(kt, Kt)` — a **runtime** predicate. GCC
folds identical branches only on a best-effort basis, and at `-O3` it did not
fold these: `mm_trisc0_unpack.S` came out **23 instructions longer** than the
same kernel compiled without the wrapper, with an extra `kt == Kt - 1` test in
the inner loop. `mm_trisc1_math.S` and `mm_trisc2_pack.S` were unaffected.

Verify by generating a control build with the wrapper rewritten to
`__VA_ARGS__` and diffing the normalised assembly; do not assume the compiler
cleaned it up.

Also worth knowing: `TRACY_ZONE_IF` in that example is guarded on
`#if defined(PROFILE_KERNEL) && ENABLE_TRACY`, and the JIT only injects
`PROFILE_KERNEL` when the host runs with `TT_METAL_DEVICE_PROFILER=1`, so that
wrapper compiles out on its own. `ENABLE_TRACY` defaults to **1** and is *not*
conditional on the profiler, so `TRACY_ZONE` itself must be switched off
explicitly or every zone lands in the `.S` as a begin/end marker pair.

## Assumed, not measured

- That a spliced `.S` is safe to combine with any kernel that uses `cb_*`/`noc_*`
  — four kernels have been exercised: the matmul example's NCRISC/BRISC/three
  TRISCs, and `add_2_integers_in_riscv`'s single BRISC kernel (which uses `noc_*`
  and no CBs at all). A kernel using circular buffers from a spliced `.S` is
  still untested.
- That the pinned symbol lists are complete for kernels other than these; they
  were derived by reading link errors, so a new kernel may need more.
  `add_2_integers_in_riscv` needed exactly the matmul dataflow list — no more,
  no less.
