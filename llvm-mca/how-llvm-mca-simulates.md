# How `llvm-mca` actually produces a cycle count

**Finding.** `llvm-mca` *is* a cycle-by-cycle state-machine simulation — but it
simulates a **timing** state machine, not a **functional** one. Instructions are
never executed, no data value is ever computed or stored, and no memory address
is ever formed. The entire "hardware" is (a) a table generated by TableGen from
`.td` files and (b) a handful of generic C++ state containers that know nothing
about any particular ISA — three of them, for an in-order model.

This explains the limitations documented in
[`tt-bh-model-accuracy.md`](tt-bh-model-accuracy.md): some hardware mechanisms
have no representation in this state machine.

Read against `llvm-project` `34152bb7d2d` (LLVM 24.0.0git).

## The main loop

`llvm/lib/MCA/Pipeline.cpp`, `Pipeline::run()`:

```cpp
do {
  if (!isPaused())
    notifyCycleBegin();
  if (Error Err = runCycle())
    return std::move(Err);
  notifyCycleEnd();
  ++Cycles;
} while (hasWorkToProcess());

return Cycles;
```

`runCycle()` is three passes:

1. `cycleStart()` on every stage, **in reverse order** (last stage first).
2. Repeatedly `execute(IR)` on `Stages[0]` (the `EntryStage`) while it
   `isAvailable()`. Instructions push themselves downstream via
   `moveToTheNextStage()`.
3. `cycleEnd()` on every stage, **in forward order**.

## Where each number in the report comes from

The report mixes two *different kinds* of number, and conflating them is the most
common way to misread `llvm-mca` output.

**Simulated — a literal loop trip count.** `Pipeline::run()` returns `Cycles`,
the number of times the loop above executed before `hasWorkToComplete()` went
false, i.e. until `RetireStage`'s control unit drained
(`Stages/RetireStage.h:41`, `return !RCU.isEmpty();`). That value is `Total
Cycles` in the summary and it is what `-timeline` draws. It is not an estimate.

**Computed statically from the table, never simulated.** `Block RThroughput`
never touches the simulation. `SummaryView::onEvent` accumulates, per retired
instruction, `Desc.NumMicroOps` and `Desc.Resources` — both straight out of
TableGen — and `collectData()` then calls `computeBlockRThroughput()`
(`lib/MCA/Support.cpp:84`):

```cpp
double Max = (double)NumMicroOps / DispatchWidth;
for each proc resource R used:
  Max = std::max(Max, (double)ProcResourceUsage[R] / R.NumUnits);
return Max;   // max(uOps/dispatch width, per-resource occupancy)
```

So `Block RThroughput` is a **bounds calculation over the static schedule
table**. It contains no dependency chains at all: it answers "if dependencies
were free, what does port/issue pressure alone imply?" — right for a
throughput-bound loop, wrong for a latency-bound one.

**Averaged over 100 repetitions.** The pipeline is not handed the block once:
`CircularSourceMgr` (`include/llvm/MCA/SourceMgr.h:59`) replays it `-iterations`
times, default `DefaultIterations = 100`. `Total Cycles` therefore covers one
pipeline fill + 100 blocks + one drain, and `IPC = TotalInstructions /
TotalCycles` is a steady-state average in which the fixed ends are amortised to
nothing. Lower `-iterations` and the ends start to matter.

## What one cycle of an in-order core actually does

`InOrderIssueStage::cycleStart()` (`lib/MCA/Stages/InOrderIssueStage.cpp:397`) —
this is the whole "hardware state machine step", seven lines of substance:

```cpp
NumIssued = 0;
Bandwidth = getIssueWidth();

PRF.cycleStart();          // register file: retire mappings whose writers finished
LSU.cycleEvent();          // load/store queue: advance memory deps

SmallVector<ResourceRef, 4> Freed;
RM.cycleEvent(Freed);      // RELEASE RESOURCES consumed in the previous cycle

updateIssuedInst();        // for each in-flight insn: cycleEvent(); retire if done
updateCarriedOver();
if (SI.isValid()) { ...tryIssue(IR)... }   // retry the instruction that stalled
```

Note `RM.cycleEvent()` frees resources at the *start of the next cycle*, not at
the end of the issuing one. That single detail is what makes `BufferSize = 0`
mean "1 IPC, in order": an instruction occupies its resource for exactly one
`cycleStart` boundary, so the next instruction issues on the very next cycle.

`cycleEnd()` (`:439`) is just `PRF.cycleEnd(); SI.cycleEnd(); --LastWriteBackCycle;`.

## There is no data anywhere

`InstructionBase` (`include/llvm/MCA/Instruction.h`) holds:

| Field | What it is |
| --- | --- |
| `const InstrDesc &Desc` | pointer into the TableGen-generated schedule table |
| `SmallVector<WriteState, 2> Defs` | one entry per register *definition* |
| `SmallVector<ReadState, 4> Uses` | one entry per register *use* |
| `std::vector<MCAOperand> Operands` | operands, kept only so `CustomBehaviour` can do alias checks |
| `unsigned Opcode` | the MC opcode |
| `IsALoadBarrier` / `IsAStoreBarrier` / `MayLoad` / `MayStore` / `HasSideEffects` / `BeginGroup` / `EndGroup` / `RetireOOO` | flags |

**There is no value field.** Not an `APInt`, not a byte buffer, nothing.

"Executing" an instruction is this, in full (`lib/MCA/Instruction.cpp`):

```cpp
void Instruction::execute(unsigned IID) {
  Stage = IS_EXECUTING;
  CyclesLeft = getLatency();          // a constant, read from the table
  for (WriteState &WS : getDefs())
    WS.onInstructionIssued(IID);
  if (!CyclesLeft)
    Stage = IS_EXECUTED;
}
```

`getLatency()` is `Desc.MaxLatency`. There is no ALU.

Advancing one cycle is this, in full:

```cpp
void Instruction::cycleEvent() {
  ...
  CyclesLeft--;
  if (!CyclesLeft)
    Stage = IS_EXECUTED;
}
```

**A register's "value" in `llvm-mca` is an integer countdown.** `WriteState`'s
only timing field is `int CyclesLeft`, documented in-source as *"On instruction
issue, this field is set equal to the write latency."* `ReadState` likewise
carries only `CyclesLeft` / `TotalCycles` / `IsReady`.

### The forwarding network is one subtraction

`WriteState::onInstructionIssued()`:

```cpp
CyclesLeft = getLatency();
for (const std::pair<ReadState *, int> &User : Users) {
  ReadState *RS = User.first;
  unsigned ReadCycles = std::max(0, CyclesLeft - User.second);  // User.second == ReadAdvance
  RS->writeStartEvent(IID, RegisterID, ReadCycles);
}
```

That `std::max(0, CyclesLeft - ReadAdvance)` *is* the bypass network. A
`WriteRes<..., 1>` plus `ReadAdvance<..., 1>` yields `ReadCycles == 0`, i.e. the
consumer reads on the next cycle with zero stall — which is exactly why a
dependent `add` chain measures 1 cycle/op and a dependent `mul` chain (latency 2)
measures 2.

## Why "who + when" is sufficient: subscription, not lookup

A read never looks a value up. It *subscribes* to its producer and is later
*notified* with a countdown, which is why a `CyclesLeft` integer is enough:

* `RegisterFile::addRegisterRead()` calls `collectWrites()` to find the pending
  writers, then for each one calls `WS.addUser(..., &RS, ReadAdvance)` -- it hands
  the producer a **pointer to the `ReadState`**. No value changes hands in that
  handshake.
* When the producer issues, `WriteState::onInstructionIssued()` pushes
  `max(0, latency - ReadAdvance)` to every subscriber through
  `ReadState::writeStartEvent()`.

Two details confirm only *time* is being conveyed:

1. **`ReadState::CyclesLeft` starts at `UNKNOWN_CYCLES`.**  A read can subscribe
   before its producer has even issued, so `DependentWrites` is a counter: the
   read becomes `IsReady` only once every dependent producer has reported, and it
   keeps `max(TotalCycles)`.  There is no `assert` that could fire for "value not
   yet known", but there is one for `CyclesLeft == UNKNOWN_CYCLES`.  A *value*
   cannot be pending; a *wait time* can.
2. **Register renaming is what makes the pair sufficient.**  `RegisterFile` keeps
   `RegisterMappings[RegID] = {WriteRef, RegisterRenamingInfo}` and honours
   `RenameAs`, so a read subscribes to the write that was current when the read
   was added rather than to "whatever writes `a5` last" (`WriteRef::PRFID` is the
   physical register).  That removes the false, name-induced dependencies; what
   is left is true data dependence, and the timing of true data dependence is
   fully determined by when the producer writes.  Nothing needs to know *what* it
   wrote.

This is also why `-mcpu=tt-bh` reports about 1.3 cycles per instruction on the
unfolded spin trace: renaming lets the poll iterations overlap, because inside
MCA they have no dependency on one another at all.  On the device the branch
creates one.

## The hardware description is 100% TableGen

```console
$ grep -rn "MCSchedModel\|SchedModel" lib/Target/RISCV/*.cpp
lib/Target/RISCV/RISCVInstrInfo.cpp:2203      # unrelated (codegen)
lib/Target/RISCV/RISCVMachineScheduler.cpp:144 # unrelated (codegen)
lib/Target/RISCV/RISCVSubtarget.cpp:33,40     # cl::opt defaults for codegen
lib/Target/RISCV/RISCVSubtarget.cpp:226,232   # getMispredictPenalty() / getLoadLatency()
lib/Target/RISCV/RISCVSubtarget.cpp:278       # hasInstrSchedModel()
```

**There is no C++ pipeline model in the RISC-V backend.** `MispredictPenalty`
and `LoadLatency` are forwarded to the *instruction scheduler* (codegen); `mca`
never reads either of them.

Everything `mca` knows lives in `RISCVSchedTensixBaby.td` and is compiled into
`MCSchedModel` + `MCProcResourceDesc[]` + `MCWriteLatencyEntry[]` +
`MCReadAdvanceEntry[]`.

Consequently `llvm-mca`'s C++ **does not know what "EX1" or "LSU" is.** It knows
"processor resource #1, `BufferSize = 0`". The hardware semantics are injected
entirely by whoever wrote the `.td`. Adding a new backend is therefore *zero
lines of C++* — and that same fact is why the model cannot be pushed beyond what
the generic abstraction can express.

## State containers, in full

For an in-order model (`MicroOpBufferSize = 0` → `Context.cpp:74`
`createInOrderPipeline`) there are exactly **three**:

| Container | State | Where |
| --- | --- | --- |
| `RegisterFile PRF` | reg → `WriteRef{IID, WriteBackCycle, WriteResID, RegisterID}` + PRF occupancy | `HardwareUnits/RegisterFile.h` |
| `ResourceManager RM` | per resource: `AvailableSlots`, `BusyResources` (`DenseMap<ResourceRef, unsigned>` = resource → freeing cycle), `AvailableProcResUnits` / `AvailableBuffers` bitmasks | `HardwareUnits/ResourceManager.h` |
| `LSUnit LSU` | load/store queue; memory deps resolved by **operand alias analysis**, not addresses | `HardwareUnits/LSUnit.h` |

An out-of-order model additionally gets `RetireControlUnit`, `Scheduler` and
`Scoreboard`. The in-order path constructs none of them —
`RetireControlUnit`'s constructor even asserts:

```cpp
assert(SM.isOutOfOrder() &&
       "RetireControlUnit is not available for in-order processors");
```

## What this design can and cannot express

| Hardware mechanism | Purely a timing state? | Modelable by `mca`? |
| --- | --- | --- |
| Issue width / in-order issue | yes | ✅ `IssueWidth`, `MicroOpBufferSize` |
| Port / pipe occupancy | yes | ✅ `ProcResource` + `BufferSize` |
| Register RAW + bypass | yes | ✅ `WriteRes` latency + `ReadAdvance` |
| Load/store ordering, store queue | mostly | ✅ `LSUnit` (operand aliasing only) |
| ROB / retire-queue backpressure | yes | ✅ — but **only on the OoO path**; an in-order model gets no `RetireControlUnit` at all |
| Cache hit/miss | no — needs an **address** | ❌ no addresses exist |
| Store-to-load forwarding | no — needs a **value** | ❌ no values exist |
| Instruction fetch / I-cache / decode | no — needs a **PC** | ❌ no PC; documented as unmodelled |
| Branch prediction, misprediction | no — needs **history** | ❌ there is no branch concept at all: `grep -ri branch llvm/lib/MCA/ llvm/include/llvm/MCA/` returns **0 hits**. A branch is an opcode occupying a resource; the direction of an input sequence is not a question the model can represent |
| Random flushes / coherence events | no — probabilistic | ❌ |

**The rule of thumb: if a mechanism can be described purely as "X is busy until
cycle N", `mca` can model it. If it needs an address, a value, a PC, or a
history, it cannot.**

## Why this matters for Tensix

The `-mcpu=tt-bh` model (see [`tt-bh-model-accuracy.md`](tt-bh-model-accuracy.md))
maps onto this abstraction as follows:

| Tensix hardware | `.td` encoding | State it creates |
| --- | --- | --- |
| 1 IPC, in-order, single issue | `MicroOpBufferSize = 0`, `IssueWidth = 1` | — (pipeline shape) |
| EX1: "previous instruction must have vacated EX1" | `TensixBabyEX1` with `BufferSize = 0` | one busy-until counter |
| EX2 (mul/FP) | `TensixBabyEX2` | one busy-until counter |
| Load/Store Unit | `TensixBabyLSU` | one busy-until counter + LSQ |
| Integer latency 1, mul latency 2 | `WriteRes<..., 1>` / `<..., 2>` | `CyclesLeft` values |
| Forwarding network | `ReadAdvance` | the subtraction above |
| `fence` (8 extra EX1 cycles) | `TensixBabyWriteFence` on `FENCE`/`FENCE_TSO` | a longer busy-until |

The arithmetic checks out: `Block RThroughput = 100` for the 84-instruction
`kernel_main` is exactly `84 + 2×8` (two `fence`s, 9 cycles each, 8 of them
beyond the base 1). That confirms the `BufferSize = 0` dispatch-hazard
mechanism is doing what it was intended to do.

And the parts that cannot be expressed:

| Tensix mechanism | Why it has no representation |
| --- | --- |
| L0 data cache (4 lines, 2 vs ≥8) | `mca` picks latency by **opcode**; it has no address, so it cannot pick by cache line |
| Retire Unit's 8-entry queue gating EX1 | in-order pipeline constructs no `RetireControlUnit` |
| I-cache / frontend fetch | documented as unmodelled; no PC in the state machine |
| ~0.8% random L0 flush | probabilistic, not a timing state |
| Forwarding failure when several writes to one register are in flight | `ReadAdvance` is a per-opcode constant |

None of these are fixable by editing the `.td`. They are outside what the state
machine can hold.

## Practical consequence

`llvm-mca` on Tensix is a **relative** tool, not an absolute one:

- Good for: comparing two instruction sequences, finding port pressure, finding
  dependency stalls, checking that a codegen change did not lengthen the critical
  path.
- Not good for: predicting an absolute cycle count for anything touching memory,
  MMIO, NoC, or the frontend — which, on Tensix, is most kernel code.

To get an absolute number for a straight-line region, instrument it (a
`DeviceZoneScopedN` window, minus the 14-cycle empty-window cost) — cheaper and
more accurate than trying to feed `mca` the answer via `# LLVM-MCA-LATENCY`.
