# A timing plan for the single-core matmul TRISCs

This note records the scope and the recommended implementation for predicting
the three compute TRISC threads in
`example/standalone/matmul_single_core/asm_kernel/`.  The input assembly is
generated by the tt-metal toolchain; the C++ source is used only to recover
loop dimensions and the meaning of the generated pushes.

## Workload shape

The checked-in metadata uses `Mt=Kt=Nt=20` (`640 x 640 x 640` BF16 matmul),
two input circular buffers with two tile slots, and an output circular buffer
with two tile slots.  The reader issues `Mt*Nt*Kt = 8000` A/B tile pairs.  The
compute C++ calls `matmul_tiles` once per pair and packs `Mt*Nt = 400` output
tiles.

The generated TRISC streams are asynchronous producers.  A scalar RISC store
which pushes a Tensix instruction, acceptance by the first Tensix FIFO,
arrival at the Wait Gate, backend dispatch, backend completion, and the
corresponding CB event are different timestamps.

For this build, the useful expansion counts are:

| thread | scalar operation | Tensix expansion |
| --- | --- | --- |
| T0 / unpack | one context MOP per input pair | one selected replay half, six unpack/config instructions per MOP for a full 32x32 tile; 8000 MOPs |
| T1 / math | one MOP per input pair | `outer=1`, `inner=4`, loop op `REPLAY(16,16,0,0)`: four replays and 64 `MVMUL`s per MOP; 512000 `MVMUL`s plus end `SETRWC`s |
| T2 / pack | one MOP per output tile | default full-tile pack MOP: `outer=4`, `inner=4`, 16 `PACR`s per MOP; 400 MOPs and 6400 `PACR`s |

The counts are derived from `llk_unpack_AB_matmul.h`, `llk_math_matmul.h`,
`ckernel_template.h`, and `llk_pack.h`; do not infer them from the number of
static `.ttinsn` source lines.  Runtime `sw` sites in the assembly are part of
the push stream and may execute thousands of times.

## External CB/NOC contract

The TRISC model should receive the reader/writer timeline as an input.  It must
use the end of the CB operation, not the NoC request issue time:

```text
input_cb0_ready[n]   = reader cb_push_back(cb0, 1) completed
input_cb1_ready[n]   = reader cb_push_back(cb1, 1) completed
output_cb_space[n]   = writer cb_pop_front(cb16, 1) completed
output_cb_visible[n] = T2 cb_push_back(cb16, 1) completed
```

`cb_wait_front` and `cb_reserve_back` are polling operations in the generated
RISC code.  A condition becoming true at cycle `t` does not branch out at `t`:
the next status load, its response latency, the dependent compare, and the
branch (including a possible misprediction bubble) still execute.  The input
timeline therefore releases a polling condition; the scalar timing engine
decides the first cycle at which the loop observes it.

If the reader/writer timeline was measured or predicted independently, feed it
as an exogenous trace and do not re-simulate its RISC.  Keep CB `pop`/`push`
acknowledgement events in the trace so the predictor can check that the two
models agree.  If output visibility is not known in advance, the writer and
T2 must be solved together because T2's push is the writer's wait-front input.

## What the existing `tt-bh` MCA model covers

`tools/llvm-mca-tensix/RISCVSchedTensixBaby.td` is still the right scalar
baseline:

* RV32 Baby-RISC is in-order, single issue (`IssueWidth=1`);
* EX1, EX2, and LSU occupancy and scalar register dependencies are represented;
* integer, multiply, divide, branch base costs and the documented fence
  resource are represented as opcode/resource rules.

The model is not a TRISC backend model.  Stock MCA has no runtime PC/value
state, branch execution, memory addresses, CB state, or Tensix FIFO.  Its
in-order path also does not construct the out-of-order `RetireControlUnit`, so
an `.td` change cannot add a real Baby-RISC retire queue.  Address-dependent L0
or MMIO latency and Manual TTSync cannot be represented by an opcode latency.

Use MCA for the scalar instruction scheduling baseline and reuse its MC parser,
`MCSchedModel`, `ResourceManager`, `RegisterFile`, and `LSUnit` data.  Do not
invoke the `llvm-mca` command separately for each C++ region: doing so resets
register readiness, LSU state, and all queue state at every cut.

## Recommended predictor architecture

Build a persistent `ttloop` driver around the MCA scalar model.  The driver has
one scalar state and one Tensix frontend/backend state per TRISC, plus shared
per-core state:

```text
Per TRISC:
  RISC PC/register values and branch predictor state
  scalar EX1/EX2/LSU/retire timing
  four-entry RISC store queue
  first Tensix FIFO (32 entries, normal acceptance watermark 28)
  MOP input FIFO (8), Replay/FIFO2 (2), replay buffer (32)
  MOP configuration and Wait Gate mask

Shared Tensix core:
  SrcA/SrcB valid/ownership handshakes
  MATH_PACK semaphore (max 2 for SyncHalf)
  UNPACK_SYNC/context state
  Dst aligned 8x16 blocks: last-write cycle, valid bits, active half
  unpacker, matrix/FPU, packer, CFG/TDMA/ADC and sync resource busy times
```

The scalar front end should be a functional RV32 trace executor (Spike or a
small interpreter can supply register values, branch targets, and effective
addresses).  Spike's functional execution time is not used.  At each executed
RISC instruction, ask the persistent scalar scheduler for the earliest EX1
cycle, then apply the instruction's effect to the queues and the functional
state.  For every conditional branch, use the real outcome and maintain a
separate branch predictor; a misprediction costs the documented four-cycle
bubble (externally five EX1 cycles).  MCA itself assumes a straight-line,
perfectly predicted stream and cannot do this step.

The scalar and backend clocks are one shared core cycle.  The scalar engine
may continue while backend instructions are queued.  It can be delayed by a
full push path, a Manual/Auto TTSync request, a memory response, or a branch
misprediction.

## Frontend and push modeling

Decode every `.ttinsn IMM32` and every executed `sw` whose resolved address is
`INSTRN_BUF_BASE` (or the thread-specific instruction buffer) into a
`PushEvent`.  The event carries the Tensix word, source PC, thread, and the
RISC store request/retire cycles.  Keep the RISC store queue separate from the
Tensix FIFOs.

The documented Blackhole transition is approximately:

```text
q0_next = q0 + accepted_words - q0_dequeue_words
```

`q0` has 32 physical entries, single-word acceptance normally stops above 28,
and a fused group can carry up to four adjacent `.ttinsn` words.  The downstream
MOP and Replay expanders emit at most one instruction per thread per cycle and
are subject to FIFO1/FIFO2 and Wait Gate backpressure.  The first implementation
should use one push per RISC instruction because this build normally disables
gathering (`ENABLE_GATHERING` is absent).  If gathering is enabled, group only
adjacent encoded `.ttinsn` instructions at their linked PCs; a runtime `sw` is
not automatically fusible.

Report these events independently:

```text
risc_store_issued, risc_store_retired,
push_request_emitted, fifo0_accepted,
mop_expanded, replay_expanded, wait_gate_passed,
backend_dispatched, backend_completed
```

Do not assign a fixed backend completion latency to a push.  A push only means
that the frontend accepted a word; it does not mean that its MOP, Replay, or
backend payload has run.

## TTREPLAY and MOP modeling

Represent `TTREPLAY` and MOP words as frontend pseudo-events, not scalar RISC
instructions with a fake long latency.

* `TTREPLAY(start,len,Exec=0,Load=1)` consumes the following `len` incoming
  Tensix words into the per-thread 32-entry replay buffer and emits no backend
  instruction.  It ingests at most one word per cycle and blocks later input
  when the input FIFO is full.
* A replay execution consumes its command and emits one recorded word per cycle,
  with downstream backpressure able to extend the run.
* T0's initial replay records 12 words and later MOPs select a six-word half.
* T1 records 16 MVMUL words.  Its template MOP emits four replay commands,
  therefore 64 MVMULs per runtime MOP, followed by the configured end `SETRWC`.
* T2's default pack template does not need a replay buffer; its configured MOP
  emits 16 PACR words per output tile and a final address-counter operation.

MOP configuration stores are ordinary RISC MMIO stores.  They program the
expander and are not backend completion events.  A `MOPExpanderDoneCheck`
(`PC_BUF_BASE+8`) waits only until MOP input has been consumed and the MOP
expander is idle; `CoprocessorDoneCheck` (`PC_BUF_BASE+4`) waits for all
in-flight Tensix work for that thread.  The `sw; lw; and` sequence around these
addresses must be modeled as an ordered Manual TTSync transaction, not as three
ordinary two-cycle scalar instructions.

## Backend dependencies for this kernel

The backend scheduler should start with the instruction classes actually
generated here:

* `UNPACR`/`UNPACR_NOP`, `RDCFG`, `ADDDMAREG`, `WRCFG`, `SETADC`, `SETDMAREG`,
  and `STOREREG` for T0;
* `MVMUL`, `SETRWC`, `SETC16`, and the MATH/CFG synchronization operations for
  T1; and
* `PACR`, `SETADC`, `SETDMAREG`, `WRCFG`, `ZEROACC`, and `STOREREG` for T2.

Each word first passes the per-thread Wait Gate.  The gate can hold the entire
thread when a `STALLWAIT`/`SEMWAIT` mask is latched or when the selected backend
unit, source bank, semaphore, mutex, or Auto TTSync dependency is unavailable.
The documented wait instructions have a one-cycle lag after their conditions
become true.

The minimum shared state is:

1. **SrcA/SrcB ownership.**  `UNPACR` waits before overwriting a bank owned by
   MATH; `MVMUL` waits until both selected banks are valid, and `SETRWC(CLR_A/B)`
   returns a bank to UNPACK.  This is the producer/consumer dependency between
   T0 and T1; CB readiness alone is insufficient.
2. **MATH_PACK.**  Startup uses `DstSync::SyncHalf`, so the semaphore max is 2.
   Math waits on max before acquiring a half and posts when a destination section
   is committed.  Pack waits on zero before reading and gets the semaphore after
   packing/clearing the half.
3. **Dst hazards.**  Track physical aligned 8x16 blocks after applying the
   configured `Adj16` mapping and active half offset.  A Dst write prevents a
   Matrix Unit or PACR read of that block during the next four cycles.  A
   `ZEROACC` clears row-valid state and is a synchronization operation; do not
   model it as an arbitrary MVMUL write.
4. **Backend resource occupancy.**  Give UNPACK, FPU, PACK, CFG/THCON, TDMA/ADC,
   and SYNC their measured issue/throughput and completion parameters.  The ISA
   does not provide all Blackhole operation latencies; calibrate these with
   isolated device probes and keep them as configuration inputs.

Auto TTSync must be discovered from the generated stream/firmware configuration.
It tracks global config, GPR, TDMA, and Tensix-instruction accesses only when the
corresponding `TENSIX_TRISC_SYNC_*` bits are enabled.  It does not synchronize
Dst, semaphores, or cross-thread dependencies.  If the enable state is unknown,
run both variants and validate against a probe before trusting a prediction.

## How to integrate with LLVM MCA

There are two reasonable implementations:

1. **Recommended:** keep `llvm-mca -mcpu=tt-bh` as the scalar B2 baseline and
   implement the persistent event/timing driver in `tt-loop-scheduler`, reusing
   LLVM MC parsing and scheduling tables.  This avoids pretending that an MCA
   `WriteRes` can express an asynchronous Tensix queue.
2. **Integrated fork:** add a `ttloop` source stage and backend-expansion stage
   to the LLVM MCA fork.  Add pseudo MC instructions for `TT_PUSH`, `TTREPLAY`,
   and `TT_MOP`; use `InstrPostProcess`/`CustomBehaviour::checkCustomHazard` for
   scalar push and MMIO hazards, and add a custom stage that emits backend words
   and consumes the external CB event trace.  The existing `InOrderIssueStage`
   still needs a persistent trace feeder and dynamic branch handling; changing
   only `RISCVSchedTensixBaby.td` is not sufficient.

The integrated fork should preserve MCA's scalar `HWEventListener` events and
add TT-specific records for FIFO acceptance, Wait Gate release, MOP/Replay
expansion, Dst stalls, and CB observations.  The CLI output should report at
least RISC return time, last push acceptance, last backend completion, each CB
push, and each Manual TTSync release separately.

## Validation order

Validate in increasing scope:

1. Straight-line scalar snippets against `llvm-mca -mcpu=tt-bh` and a device
   `mcycle` bracket.
2. Poll loops with a synthetic CB-ready cycle; verify that the condition release
   cycle is earlier than the branch-out cycle and that misprediction policy is
   explicit.
3. Push bursts with a blocked Wait Gate; check FIFO0 watermark, store-queue
   stalls, and gathering-on/off behavior using the existing FIFO probe.
4. T0 replay/MOP expansion and T1 replay/MOP expansion independently, checking
   expansion counts and `PC_BUF_BASE+8` versus `+4` semantics.
5. T0+T1 source-bank handshake and T1+T2 MATH_PACK/Dst synchronization.
6. Full single-core matmul with reader/writer CB/NOC timestamps supplied as an
   input trace.  Compare `last backend completion`, T2 `cb_push`, and the final
   writer acknowledgement separately from each TRISC's scalar return.

The result should expose a breakdown rather than one opaque cycle count.  A
single total is meaningful only after the event boundaries and the calibration
configuration are included in the report.
